## MM-041 | Order confirmation page accessible via direct URL after logout

**Severity:** High
**Priority:** High
**Status:** Closed — Fixed

**Summary:** The checkout complete page (`/checkout-complete.html`) was accessible via direct URL navigation after the user had logged out. A logged-out user could view the confirmation page, which may contain order summary details.

**Steps to Reproduce:**
1. Complete a checkout flow — note the confirmation URL
2. Logout via the sidebar
3. Paste the confirmation URL directly into the browser

**Expected Result:** User redirected to login page with an error.
**Actual Result:** Checkout complete page renders without authentication.

**Fix Verified:** Session guard added to checkout complete route. Confirmed fixed in v1.3.2.

## MM-042 | Incorrect item count in order summary when cart modified mid-checkout

**Severity:** High
**Priority:** High
**Status:** Closed — Fixed

**Summary:** If a user opens a second browser tab, removes an item from the cart in that tab, and then continues the checkout flow in the original tab, the order summary on step two displays the old item count — leading to a mismatch between what the user sees and what would be ordered.

**Steps to Reproduce:**
1. Add 2 items to cart in Tab A
2. Proceed to checkout step one in Tab A (do not submit yet)
3. Open Tab B — navigate to cart — remove one item
4. Return to Tab A — click Continue on step one

**Expected Result:** Step two reflects current cart contents (1 item).
**Actual Result:** Step two shows original 2 items — stale cart state.

**Fix Verified:** Cart state now refreshed from server on step two load.

**Priority:** Critical
**Status:** Closed — Fixed

**Summary:** By navigating directly to `/checkout-step-two.html` after clearing the cart via Reset App State but without navigating away from step one, a user could reach the order summary with zero items and complete a zero-value order.

## MM-045 · MM-047 | CRITICAL — Race condition in checkout confirmation causes inventory desync

**Severity:** Critical
**Priority:** P0 — Blocker
**Status:** Closed — Fixed (Pre Go-Live)

**Summary:** A critical race condition was identified in the checkout confirmation flow. When the "Finish" button was double-clicked or the confirmation request was fired twice in rapid succession (e.g., due to network retry), the order was marked as complete in the UI but the inventory decrement call either fired twice or was skipped entirely — depending on which response resolved first.

**This bug was caught pre go-live during automated regression testing.**

**Steps to Reproduce:**
1. Add any item to cart
2. Proceed through checkout — reach step two
3. Using Playwright `dblclick()` on the Finish button, trigger two simultaneous submission events
4. Observe network requests in DevTools — two POST requests to the order endpoint

**Expected Result:**
- Order created exactly once
- Inventory decremented exactly once
- Button disabled after first click to prevent re-submission

**Actual Result (before fix):**
- Two order submission events fired
- Inventory count either double-decremented or not decremented at all
- UI showed confirmation but server state was inconsistent
- No button disable on first click

**Evidence:**
- Playwright test: `TC-PAY-034` and `TC-PAY-035` expose this behaviour
- Network waterfall shows two concurrent POST requests within 50ms of each other
- Server logs confirm duplicate order IDs created in test environment

**Risk Assessment:**
In a production payment integration, this race condition would have caused:
- Duplicate charges to the customer's payment method
- Incorrect inventory levels leading to overselling
- Order fulfilment mismatches

**Root Cause:** The "Finish" button had no `disabled` state applied after the first click, and the click handler did not implement debouncing or idempotency checks.

**Fix Applied:**
- Button disabled immediately on first click event
- Debounce added to order submission handler (300ms)
- Server-side idempotency key added to order endpoint
- Client-side check: if order already submitted, subsequent clicks are no-ops

**Fix Verified:** Confirmed resolved in v1.4.0 — pre go-live. Zero duplicate orders in 500 automated test runs post-fix.

**Tester Note:** This bug was identified exclusively through automated Playwright testing. The double-click timing window (< 100ms) makes it extremely unlikely to be caught during manual testing alone. This demonstrates the value of automation for race condition detection.
